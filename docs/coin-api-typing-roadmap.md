# Coin API typing and binding-friendliness roadmap

This document records the first source-backed review of the ranked Coin API
typing queue. It is intentionally an additive modernization roadmap: the
existing C++ ABI remains valid, while new value-oriented entry points or Pivy
adapters can be introduced without coupling the work to SWIG 4.5.

The machine-readable source of this review is
[`tools/pivy_typing/coin_api_roadmap.py`](../tools/pivy_typing/coin_api_roadmap.py).
The report generated by `pixi run typecheck_binding_friendliness` includes the
same decisions, native declarations and provenance.

## Decision summary

The first 20 ranked methods contain three different kinds of work:

| Owner | Count | Meaning |
| --- | ---: | --- |
| A — typing/backend | 0 | No reviewed entry in this slice needs only a renderer or type-policy fix. |
| B — Pivy binding | 5 | The existing Coin ABI is sufficient; Pivy can add a safe adapter or value-returning helper. |
| C — Coin API | 2 | Borrowed or variable-length native data needs an additive owning/value API. |
| D — intentionally native | 13 | Platform handles, thread ABIs and untyped native utilities should remain outside the supported typed Python surface. |

The remaining ranked queue is still present in the report, but remains
provisional until it receives the same source-level review. This distinction
prevents a heuristic classification from being mistaken for a Coin design
decision.

The five reviewed Pivy-binding entries have now been addressed without adding
Coin APIs: `SoConvexDataCache.generate`, `SoShapeHintsElement.get`,
`SoFieldContainer.getFieldsMemorySize` and the scalar `SoInput` readers are
closed in the typing model; `SbTime.getValue` is partial because its scalar
outputs are typed while the platform-specific `timeval *` overload remains an
intentional native boundary. The registry keeps these statuses as review
history, so completed work is not mistaken for an open Coin queue item.

## Implementation order

The reviewed decisions imply three additive workstreams:

1. **Pivy adapters first:** the five low-risk B entries in this slice are now
   implemented and tested. Continue with the remaining existing Pivy APIs,
   especially safe scalar/output and ownership-preserving adapters, before
   proposing any Coin API changes.
2. **Coin proposals:** prototype the two C result objects without removing
   the old methods. Validate ownership, copying cost and behavior in native
   Coin tests before exposing them through Pivy.
3. **Native boundary policy:** keep the 13 D entries explicitly documented
   as native. Do not spend typing budget replacing them with `Any`, guessed
   handles or unsafe callback protocols.

After those slices, review the provisional tail in descending score. Each
new decision should add a source header, the exact declaration, an owner and a
testable next action to the registry before changing generated annotations.

## What this does not propose

This roadmap does not replace SWIG, change packaging, redesign CMake, or
modify Coin's existing ABI. It also does not claim that every current
`Incomplete` boundary is a Coin defect. The resolved manifest remains the
canonical inventory; this document only assigns ownership for the highest
impact queue and gives future Coin 4.x/Coin 5.x work a reviewable order.
